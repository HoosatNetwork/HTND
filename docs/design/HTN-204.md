# HTN-204 — the trusted DAA window after a prune

**Status: Option 0 implemented.** See §9. The analysis below is what led to that choice and is kept
because it is the record of why the obvious fix is wrong.

Options (i) and (ii) remain open and are **not** implemented. They are about robustness in cases
Option 0 does not reach, not about the reported symptom.

---

## 1. The symptom

A node that has just completed a headers-proof IBD mines at **genesis difficulty**. On mainnet that
is `0x1E7FFFFF` → a difficulty ratio of 65536.0078, reported as `65536.01`, against a real network
difficulty around `1.3e8` — roughly 2000× too easy.

The measurement that pinned it, from the original live investigation:

- `GetBlockDagInfo`: difficulty `65536.01`, `virtualDaaScore` 227416484, pruning point at DAA
  227414422.
- The difference is **2062** blocks. `EstimateNetworkHashesPerSecond` stops changing once the
  requested window exceeds what actually exists; it was still changing at 2050 and identical from
  2060 up. So the window held exactly the blocks above the pruning point and nothing below it.
- Mainnet version 9 wants a window of **2640**. With only 2062 available,
  `difficultymanager.go`'s `targetsWindow.len() < dm.windowSize(blockVersion)` returns
  `dm.genesisBits`.
- The pruning point's `selectedParentHash` was `fefefefe…fe` — `model.VirtualGenesisBlockHash` —
  because it arrived through `validateAndInsertBlockWithTrustedData`.

## 2. Why it happens

`calculateBlockWindowHeap` (`domain/consensus/processes/dagtraversalmanager/window.go`) walks down
the selected chain looking for a block that carries a trusted DAA window, and takes that window when
it finds one.

The loop currently reads:

```go
if selectedParent.Equal(dtm.genesisHash) || selectedParent.Equal(model.VirtualGenesisBlockHash) {
    break
}

_, err := dtm.daaWindowStore.DAAWindowBlock(dtm.databaseContext, stagingArea, current, 0)
currentIsNonTrustedBlock := database.IsNotFoundError(err)
```

The pruning point is *precisely* the block whose selected parent is the virtual-genesis marker and
whose window exists only as trusted data. So the walk breaks **one statement before the lookup it
came for**. The pruning point's window is empty.

`BlockWindowHeapSlice` caches that empty result, and every child builds its window from its selected
parent's cached slice, so the truncation is inherited by everything above the pruning point. Until
2640 fresh blocks accumulate, every template carries genesis bits.

Upstream kaspad has no such break and reaches the trusted window. The break arrived in `8056a76ee`
and was folded into the genesis condition by `fbbe4ebaa`.

**The diagnosis is not in question.** What follows is about the fix.

## 3. Why the recorded fix is unsafe

The recorded fix moves only the `VirtualGenesisBlockHash` break to after the trusted-window branch,
keeping it as a guard before the `ghostdagDataStore.Get` that would otherwise look up the marker.

It makes `TestIBDWithPruning` fail reproducibly. This was re-verified against the current tree for
this document (see §4), not taken on trust.

The failure is on the **serving** side, not the mining side:

```
Non-critical peer protocol error from HandlePruningPointAndItsAnticoneRequests:
database entry not found ... DAA window <hash> does not exist in db
Timeout waiting for IBD to finish
```

### The mechanism

`calculateBlockWindowHeap` has two callers with incompatible requirements, and they are genuinely
the same code path in the current tree:

| Caller | Wants |
|---|---|
| difficulty | the **true** window, including trusted data — this is what HTN-204 is about |
| trusted-data serving | only blocks it can actually **serve** headers and GHOSTDAG data for |

The serving path, confirmed in the tree:

```
app/protocol/flows/v8/blockrelay/handle_pruning_point_and_its_anticone_requests.go:82
  → Consensus().BlockDAAWindowHashes
  → consensus.go:1655 dagTraversalManager.DAABlockWindow
  → BlockWindow → BlockWindowHeapSlice → calculateBlockWindowHeap
```

With the fix applied, a serving node's window for the pruning point stops being empty and becomes
the full trusted window. The serving loop then asks `TrustedDataDataDAAHeader` for each block in it.
That answers from `ghostdagDataStores[0]`, or failing that from `blocksWithTrustedDataDAAWindowStore`
keyed by `(trustedBlockHash, daaBlockWindowIndex)` — and for those blocks the serving node has
**neither**. It returns not-found, and the syncing peer's IBD dies.

**The empty window was, accidentally, what kept the serving path consistent.** That is the whole
difficulty of this ticket: the bug and the thing preventing a worse bug are the same line.

## 4. Reproduction against the current tree

The attempt patch is not in the repository (it was kept in a scratchpad that no longer exists), so
it was reconstructed from the ticket's description — split the combined break, leaving the
virtual-genesis guard immediately before `ghostdagDataStore.Get`:

```go
if selectedParent.Equal(dtm.genesisHash) {
    break
}
// ... trusted-window branch ...
if selectedParent.Equal(model.VirtualGenesisBlockHash) {
    break
}
selectedParentGHOSTDAGData, err := dtm.ghostdagDataStore.Get(...)
```

Result on this branch, `HTND_PEBBLE_CACHE_MB=300 HTND_MEMTABLE_SIZE_MB=32`, alternating against the
unpatched tree:

| Tree | Runs | Outcome | Duration |
|---|---|---|---|
| With the attempt patch | 3 | **3/3 FAIL** | ~34s each (the IBD timeout) |
| Unpatched (control) | 2 | **2/2 pass** | ~6.3s each |

Every failing run produced the same error, with a different block hash each time:

```
database entry not found in HandlePruningPointAndItsAnticoneRequests:
DAA window 4eae8a35…5641 does not exist in db:
key 012f6461612d77696e646f772f4eae8a35…56412f0000000000000000 not found
--- FAIL: TestIBDWithPruning (33.92s)
    ibd_test.go:122: Timeout waiting for IBD to finish.
```

The key decodes as prefix `01`, bucket `/daa-window/`, the block hash, then index `0` — a
`blocksWithTrustedDataDAAWindowStore` lookup for a block the serving node has no trusted data for.
That is the mechanism in §3, observed directly rather than inferred.

The three failures naming three different hashes matters: this is not one unlucky block. The serving
node is being asked for trusted data for whichever blocks the now-populated window happens to
contain, and it has none of them.

**The refutation holds against the current tree.** The patch must not be re-applied as written.

## 5. Options

### Option 0 — separate the two uses (not in the plan's list, but implied by the refutation)

Give the serving path its own function that enumerates only blocks the node can serve trusted data
for, and let the difficulty path take the trusted window. `DAABlockWindow` already exists as a
distinct entry point and is used *only* by `BlockDAAWindowHashes`; it simply delegates to the shared
`BlockWindow` today.

- **Effort:** smallest of the options. No new data, no migration, no format.
- **Data format:** none.
- **Migration:** none.
- **IBD-serving implications:** this *is* the serving change — the serving window's contents become
  explicitly "what I can serve" rather than incidentally so. It is protocol-visible: it changes what
  a node hands a syncing peer.
- **Risk:** the serving window must remain a valid DAA window from the peer's point of view, not
  merely a subset. If the peer reconstructs difficulty from what it was served, serving a truncated
  window reintroduces this very bug on the peer. **This needs checking before the option is
  chosen** — it is the question that decides whether Option 0 is a real fix or a bug relocation.
- **Recommended first step regardless of which option is chosen**, because every other option still
  has to answer the same serving question.

### Option (i) — persist a compact trusted window at prune time

When pruning, write a compact, self-contained record of the pruning point's DAA window, and have
`calculateBlockWindowHeap` read that rather than walking into pruned territory.

- **Data format:** a new store keyed by pruning point hash, holding the window's
  `(hash, GHOSTDAGData)` pairs — the same shape `windowHeap.tryPushWithGHOSTDAGData` consumes. Size
  is bounded by the window size (2640 on mainnet v9) × per-entry size, so single-digit MB. It must
  be versioned, because the window size is per block version and a future fork changes it.
- **Migration:** existing nodes have no such record. Either it is written lazily on the next prune —
  meaning a node that already pruned stays broken until it prunes again — or a one-shot backfill
  reconstructs it from retained headers at startup, which is only possible if those headers are
  still retained. The backfill is the awkward part and needs its own design.
- **IBD-serving implications:** this record is *this node's* view. If it is also served, two nodes
  that pruned at different times could serve different windows for the same pruning point, which is
  a new disagreement surface of exactly the kind HTN-001/002/005 are about. Safer to keep it local
  and never serve it — which means it does **not** on its own fix the serving side, so Option 0 is
  still needed alongside it.
- **Strength:** the node's own difficulty becomes correct immediately and deterministically.
- **Weakness:** new persistent state, a migration, and a new way for two nodes to disagree if it
  ever leaks into what is served.

### Option (ii) — derive from retained headers plus a checkpointed window in the release

Reconstruct the window from headers the node retains after pruning, and ship an explicit checkpoint
window in the release for the case where they are not retained.

- **Data format:** no new store. The checkpoint is a release artefact — a pruning point hash plus
  its window — shipped the way `POWScores` is.
- **Migration:** none for existing nodes; they gain the behaviour by upgrading.
- **IBD-serving implications:** the checkpoint is identical on every node running the release, so it
  cannot produce the per-node divergence Option (i) risks. That is its main advantage.
- **Weakness:** it is only as good as the checkpoint. A node syncing to a pruning point *newer* than
  the shipped checkpoint falls back to the retained-headers path, and the original evidence shows
  headers were retained for only 400+ blocks below the pruning point against a 2640 window — so the
  fallback is **insufficient on its own** and would still produce genesis bits. Whether more headers
  can be retained, and at what storage cost, is an open question this option depends on.
- **Coupling:** it puts a consensus-relevant constant in the release, so every release becomes a
  coordination point. That is the same shape as choosing an activation DAA score, so it is not a new
  kind of burden — but it is a recurring one rather than a one-off.

## 6. Comparison

| | Option 0 | Option (i) | Option (ii) |
|---|---|---|---|
| Fixes mining difficulty | no, alone | yes | only up to the checkpoint |
| Fixes IBD serving | yes | no, alone | no, alone |
| New persistent state | none | yes | none |
| Migration needed | none | yes, and awkward | none |
| New divergence surface | if the served window is wrong | if the record is ever served | none |
| Recurring release burden | none | none | yes |

**Option 0 is not an alternative to (i) and (ii) — it is a prerequisite for both.** Neither (i) nor
(ii) fixes the serving failure that sank the original patch, because both make the difficulty window
non-empty and the serving path shares it.

A defensible shape is therefore: **Option 0 first**, verified against `TestIBDWithPruning`, then
(i) or (ii) for the difficulty side. My inclination is (ii), because it cannot make two nodes
disagree, but it depends on an unanswered question about header retention that (i) does not.

## 7. Required test

From the plan, and it is the right test:

> A node synced from a headers proof and a node synced from genesis must produce identical bits for
> the first post-activation template.

Shape: build a chain long enough to move the pruning point; sync node A from genesis and node B from
a headers proof; call `BuildBlockTemplate` on both; assert `Header.Bits()` is equal.

Today this fails on B with genesis bits. It is a stronger statement than "B's window is non-empty",
because it is the property that actually matters — two nodes that disagree about difficulty build
blocks each other may reject once HTN-007's gate activates.

Add to it, since the original patch's failure was invisible to a difficulty-only test:

- `TestIBDWithPruning` must still pass — B must be able to **serve** what it now knows.
- A third node syncing **from B** must also reach the same bits. That is the case that catches a
  served window which is self-consistent but wrong, which is precisely how the offset-baseline
  problem in HTN-005 propagates.

## 8. What this does not decide

- Which option to take.
- Whether the serving window may legitimately be a subset of the difficulty window — the question
  Option 0 rests on.
- Whether more headers can be retained below the pruning point, and at what cost — the question
  Option (ii) rests on.

These are maintainer decisions. Per the plan, implementation stops here until one is chosen.

## 9. What was implemented

Option 0, and only Option 0: the two uses of `calculateBlockWindowHeap` are separated by an
`includeTrustedWindow` parameter.

| Caller | `includeTrustedWindow` | Behaviour |
|---|---|---|
| `difficultyManager.blockWindow` | **true** | walks into a pruned block's trusted window — the fix |
| `DAABlockWindow` (serving) | false | unchanged |
| `pastMedianTimeManager` | false | unchanged |
| `pruningManager.blocksToKeep` | false | unchanged |

`BlockWindow` passes `false` for all three of its callers, so the only behaviour that changes
anywhere in the tree is the difficulty window.

The virtual-genesis break is now conditional, and a second, narrower guard was added immediately
before the `ghostdagDataStore.Get` on the marker — the guard the old break happened to provide.

### The cache had to change too

`windowHeapSliceStore` was keyed by `(blockHash, windowSize)`. Once the two paths can return
different answers for that key, a shared entry means whichever ran first silently decides what the
other sees — either difficulty gets an empty window and the node still mines at genesis difficulty,
or serving gets the trusted window and kills a peer's IBD. Neither would look like a cache bug.

`includeTrustedWindow` is therefore part of both the staging-shard key and the LRU key.

While doing that, `LRUCache.evictRandom` was fixed: it rebuilt the key from its own fields, which
was merely pointless with a two-field key but would have evicted the wrong entry — or none, letting
the cache grow past capacity — once a third field existed.

### Verification

| Check | Result |
|---|---|
| `TestIBDWithPruning` (the failure that sank the original patch) | **3/3 pass**, ~6.4s — same as the control |
| `TestDifficultyWindowReachesTheTrustedWindowOfAPrunedBlock` | passes; **fails with 0 blocks instead of 10** when the fix is reverted |
| `TestServingWindowStopsAtThePruningBoundary` | passes — serving still returns 0 |
| `TestTheTwoWindowsDoNotShareACacheEntry` | passes in both warm-up orders |
| dagtraversalmanager, difficultymanager, pastmediantimemanager, pruningmanager | all pass |

The reproduction matches the ticket's own description of the original attempt's test exactly: 0
blocks in the window before, 10 after.

## 10. The implication that needs a decision before deploying

**This changes more than the bits.** `difficultyManager.blockWindow` feeds two things:

1. `requiredDifficultyFromTargetsWindow` → the header's `bits`. Not validated by anything today
   (HTN-007), so this half cannot change which blocks are accepted.
2. `stageDAAScoreAndAddedBlocks` → `daaScore = selectedParentDAAScore + len(daaAddedBlocks)`, where
   `daaAddedBlocks` is the block's merge set intersected with the window.

A larger window can only find *more* merge-set members, so a block's computed DAA score can
increase. DAA score is not cosmetic: it selects the block version (`BlockVersionForDAAScore`), and
through that K, finality depth, pruning depth and the HTN-216 coinbase gate; `daaAddedBlocks` itself
feeds `calcMergedBlockReward`.

**Why this is still convergence, not divergence.** A genesis-synced node already computes the full
window and therefore the higher, correct DAA score. The truncation only ever affected headers-proof
nodes. So this moves them *toward* the answer the rest of the network already has — it removes a
disagreement rather than creating one. That is the same argument HTN-221 was deployed on, with one
difference worth stating plainly: HTN-221 only moved bits, and this moves DAA score.

**The transition wrinkle.** `daaBlocksStore` is persistent. A node that already synced keeps the DAA
scores it computed under the truncated window for blocks it has already processed; only newly
processed blocks get the corrected computation. The in-memory `windowHeapSliceStore` clears on
restart, but the stored DAA scores do not. A clean resync is the only way to make a node's whole
history consistent with the fix.

**Recommendation:** deploy to one node and compare `GetBlockDagInfo`'s `difficulty` and
`virtualDaaScore` against a known-good genesis-synced node before rolling out. If the DAA-score
movement is judged too risky to take ungated, the difficulty call site is a one-line place to put a
version gate — but gating it means freshly synced nodes keep mining at genesis difficulty until
activation.

## 11. Correction: the first implementation only worked for one hop

§9 above describes the first change, which left the served window truncated. **That was wrong, and
it is why the fix did not work on a live node.**

The earlier "TestIBDWithPruning 3/3 pass" did not show otherwise, because that test runs on simnet,
which sets `DisableDifficultyAdjustment` — it never computes a difficulty at all. It proved serving was
not broken; it said nothing about difficulty. That claim was stated as verification of the fix and
should not have been.

A real end-to-end test, with difficulty adjustment enabled and a window smaller than the syncer's
history but larger than what the syncee has above its pruning point, showed:

| Sync path | First change | Final change |
|---|---|---|
| genesis → headers-proof | 20/20 window, correct bits | 20/20, correct |
| genesis → HP → HP (two hops) | **15/20, genesis bits** | 20/20, correct |
| three hops | — | 20/20, correct |
| HP node whose pruning point then advances, serving a new node | — | 20/20, correct |

On a real network most peers were themselves headers-proof synced, so each served its truncated
window and the next node inherited it. Reading the trusted window correctly cannot fix a window that
arrived short. That is also the most likely reason the live node received only ~400 blocks of trusted
window against the 2640 it needs.

### What changed to fix it

1. **Serve the trusted window.** `DAABlockWindow` now uses `includeTrustedWindow=true` — the same
   window difficulty is computed from.
2. **Find trusted-window blocks by hash.** `TrustedDataDataDAAHeader` fell back to reading the
   trusted-window store *by the index in the served list*, and returned whatever entry was there
   without checking its hash. The store is indexed by position in the window *as received*. Once
   serving includes trusted blocks those orders diverge: it returned another block's GHOSTDAG data
   or ran off the end. That — not "the serving node has no data" — is the precise cause of the
   failure that sank the original patch. It now tries the index, trusts it only if the hash matches,
   and otherwise searches by hash.
3. **Search the right window.** Once a headers-proof node's pruning point advances past the one it
   synced to, the new pruning point has no trusted window of its own; the bottom of its window is the
   *old* pruning point's, stored under the old hash. The lookup now finds that anchor by the same rule
   `calculateBlockWindowHeap` uses to take it, so the two agree by construction. Without this step,
   `TestIBDWithPruning` failed 3/3 with *"block X is not in the trusted DAA window of Y"*.

Each of the three is load-bearing, and each was shown failing without it: no difficulty change → 0 of
10 blocks; no serving change → 15/20 at two hops; no anchor search → IBD 3/3 fail.

### Checked rather than assumed

`blocksToKeep` still uses the non-trusted window. That is safe: `pruningManager.deleteBlock` removes
the multiset, acceptance data, body, UTXO diff and DAA score, but **never headers or GHOSTDAG data**,
and the trusted-window store has no delete at all. Everything serving reads survives pruning.

### Mixed-version networks

This is protocol-visible: it changes what a node serves. A node on the new code syncing from a peer
on the **old** code still receives that peer's truncated window and still starts at genesis
difficulty, recovering only as its own window fills. The fix reaches a node fully only when the peer
it syncs from is also on the new code. That argues for getting it onto the nodes other nodes sync
from — seeds and well-connected public nodes — first.
